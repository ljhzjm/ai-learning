## 今日踩的坑

### 1. 实验设计坑:整批塞入 ≠ 逐条调用(最值钱的一条)

第一版脚本把整个 `TITLES` 列表 `.format(title=TITLES)` 塞进一个 prompt,变成 **1 次调用**而不是 16 次。实测 zero-shot 和 few-shot 输出**一模一样的 8 行标签**,看起来像"few-shot 没用"。

**真相是:整批塞进去时,模型自然会按行对齐输出——"格式是否稳定"这个现象根本暴露不出来。** 改成逐条调用后对比才有意义(虽然最终结论仍是"没差别",但那是**可信的**没差别)。

**教训:做对比实验,"怎么调用"本身就是实验设计的一部分,不只是"问什么"。**

### 2. prompt 自相矛盾

原抽取 prompt 写「严格按 `人名:... / 公司:... / 地点:...` 一行一个字段输出」——**说"一行一个字段",布局却用 ` / ` 分隔**。模型只能猜。改成真的多行布局后,格式稳定性明显提升。

**教训:给模型的格式要求,要"说"和"示范"一致。**

### 3. 角色和指令放错槽位

原来把约束/few-shot 示例塞进了 `system`,`user` 只剩「请分类」一个空壳。能跑,但把今天要学的**「角色 vs 指令」的边界搞混了**——角色的活是 `system` 干的,指令/约束/few-shot 的活是 `user` 干的。

### 4. Windows 编码坑(第 N 次)

模型爱吐 emoji(😊💪),GBK 控制台 `print` 直接 `UnicodeEncodeError`。

**根治方案(已加进所有脚本)**:

```python
import sys
sys.stdout.reconfigure(errors="replace")   # 保留原编码,装不下的字符降级成 ? 而不是崩
```

比 `PYTHONUTF8=1` 更省事——不用每次记着加环境变量。

### 5. max_tokens 截断会伪造结论

约束实验里"无约束"那档如果沿用 `max_tokens=300`,长回答会被截断,**看起来像"约束让它变短",其实是被截的**——对比直接失效。改成 800 后"无约束"自然跑完 688 tokens,对比才成立。

# 第 3 周·周四 · 结构化输出(practice/w3d4-structured-output)

## 5 行速记

1. **学了**:三档结构化输出强度——纯 prompt(自然语言请求 json)/ JSON mode(`response_format`)/ tool 强制(`tools` + `tool_choice`);Pydantic schema 同时喂给模型和校验程序;失败重试带错误回灌
2. **最漂亮的一处设计**:schema 只写一遍——`Extraction.model_json_schema()` 生成给模型看的 schema,`Extraction.model_validate()` 校验模型给的东西,**两边同一份定义,不会漂**
3. **实测(12 条 × 3 档)**:**三档全是 12/12**——又没验证出"自然语言约束不可靠"这个预判结论(和昨天 few-shot 一模一样的模式)。DeepSeek 在这个 schema 上表现得太好了
4. **但 tool 档出现了全场唯一一次重试**(第 12 条:英伟达黄仁勋那条,首次没吐出 `tool_calls`)——复跑 5 次全过,**是偶发不是必然**。结论反转:**最强的机制也需要重试兜底**
5. **格式 100% 可靠 ≠ 内容正确**:三档全都把「蔡崇信」那条的日期抽成了 `2025年`/`2025`(真实日期是"昨日"),全都从"2025全球数字贸易博览会"里抠出了年份——**格式由机制保证,内容仍然只能靠模型**

## 三档强度对照表(今天的核心)

| 档位 | 手段 | 保证什么 | 不保证什么 |
|---|---|---|---|
| ① 纯 prompt | 自然语言约束 | 什么都不保证 | 全靠模型自觉 |
| ② JSON mode | `response_format={"type":"json_object"}` | **语法合法的 JSON** | 符合你要的字段结构 |
| ③ tool 强制 | `tools` + `tool_choice` | 字段名/类型按 schema 走 | 值对不对 |

## 今日踩的坑

### 1. JSON mode 的 prompt 里必须出现 "json" 字样

不加直接 400:

```
{"error":{"message":"Prompt must contain the word 'json' in some form to
use 'response_format' of type 'json_object'.","type":"invalid_request_error"}}
```

### 2. tool 调用的三个反直觉点(实测确认)

1. **结果不在 `content` 里**——`content` 是**空字符串**,东西全在 `tool_calls[0]["function"]["arguments"]`
2. **`arguments` 是字符串不是 dict**——得再 `json.loads` 一次。模型吐的是"JSON 文本",不是结构化对象
3. `finish_reason` 是 `"tool_calls"`,不是 `"stop"`

### 3. 「合法 JSON」≠「符合 schema 的 JSON」

**预备探针(写指导时跑的)**:给一个没指定字段名的裸 prompt 开 `json_object`,返回的是

```json
{"type": "json_object", "name": "李明", "company": "星辰科技"}
```

**它把 `response_format` 的参数原样抄成了结果字段。** 这段 JSON 语法完全合法,`json.loads` 一点脾气没有——但程序拿到 `type` 会懵。

**诚实补充**:今天正式跑的时候这个现象**没有复现**——因为 `PROMPT_ONLY` 里明确列了字段名(`name/company/place/date/amount`),模型老老实实照做了。

**所以这条坑是有条件的:JSON mode 只保证语法,字段结构对不对取决于 prompt 写得够不够死。** 换个说法就可能翻车——这正是"机制不完整"的地方,也是为什么要再叠一层 Pydantic。

### 4. tool mode 的 args 会缺字段(但 Pydantic 兜住了)

第 12 条实测返回:

```json
{"name": "黄仁勋", "company": "英伟达", "place": "东京", "date": "下月"}
```

**`amount` 字段直接不见了**——不是 `null`,是压根没出现。因为 `Extraction` 里它默认 `None`,`model_validate` 照常通过。

**这是"全部字段 Optional"这个设计决策的回报**:字段缺失被当成"这条新闻没提"而不是"程序错了",重试逻辑就不会被误触发。

### 5. 重试必须带信息(指导里的坑,原样踩了)

第一版 `extract_with_retry` 的 `except` 块里写了:

```python
messages = messages + [...]     # NameError: messages 在这个作用域里不存在
```

两处问题:①`messages` 未定义,这行一旦执行就炸;②就算定义了就绪,重试时调的仍是 `fn(s, news)`——**那串精心拼的错误信息根本没传进去**,等同原地重试。

**正确做法**:让策略函数接受 `hint` 参数,把上次的错误拼进 prompt:

```python
def extract_tool(s, news, hint=None) -> dict:
    prompt = PROMPT_TOOL.format(news=news)
    if hint:
        prompt += f"\n\n上次的输出不合格:{hint}。请只输出修正后的 json。"
    ...
```

## 一句话总结

> **自然语言约束是"请",schema 是"必须"——prompt 让模型"想"守规矩,schema 让程序"知道"它守没守。**
>
> 但对 DeepSeek + 简单 schema 的组合来说,**"请"已经够用了**(三档全 12/12)。机制的价值不在"更准",在于**它把不确定的东西变成了程序能判断的东西**——所以能重试、能报警、能在模型换版本的那天不静默崩掉。
