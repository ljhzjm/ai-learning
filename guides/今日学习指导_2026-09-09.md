昨天待办 API 已经落库 PG,但表结构是 `Base.metadata.create_all()` 建的——那是"脚手架"。真实项目里表结构会**不断演进**:加字段、改类型、删表,而库里已有数据不能删了重建。今天学 **Alembic**:表结构的"git"——每次变更写成一个**迁移文件**,可追溯、可回滚、团队可协作。

**为什么 create_all 不够用?** ① 它只会建表,不会**改**已有的表;② 已有数据的表不能 drop 重建;③ 部署上线时,新版本的表结构变更靠什么执行?迁移文件就是答案:一条 `alembic upgrade head` 把库升到最新结构。

**今天在哪个项目做?** 继续用昨天的 `practice/w2d3-sqlalchemy-todo`——给一个已有应用"补上迁移管理"才是真实工作流(独立小练习看不出价值)。迁移文件随项目一起提交。

## 🎯 先懂 5 个概念(10 分钟)

| 概念 | 一句话解释 |
|---|---|
| **迁移(migration)** | 表结构变更的"版本化代码":一个文件描述一次结构变更(建表/加列/删列) |
| **版本链** | 每个迁移文件有唯一 `revision` id 和 `down_revision`(指向前一个版本)→ 单向链表,顺序即历史 |
| **upgrade / downgrade** | `upgrade head` 升到最新;`downgrade -1` 回退一步。每个迁移文件里这两件事都写好了 |
| **autogenerate** | 对比"模型(metadata)"与"真实库"的差异,**自动生成**迁移草稿——但要人工检查后再用 |
| **alembic_version 表** | Alembic 在库里建的一张表,记录"当前在第几个版本"。`alembic current` 看的就是它 |

## 📜 第 4 步:首次迁移(30 分钟)

```powershell
uv run alembic revision --autogenerate -m "init todos table"
```

命令含义:`revision` = 新建一个迁移文件;`--autogenerate` = 对比模型与库自动写内容;`-m` = 迁移说明文字。

打开 `alembic\versions\` 下新生成的文件,**逐行读懂**(这是今天最该花时间的部分):

```python
"""init todos table

Revision ID: xxxxxxxx
Revises:
Create Date: 2026-09-09 ...
"""
from alembic import op
import sqlalchemy as sa

# revision identifiers, used by Alembic.
revision = 'xxxxxxxx'
down_revision = None          # 第一个版本没有"上一个"
branch_labels = None
depends_on = None

def upgrade() -> None:
    op.create_table('todos',
        sa.Column('id', sa.Integer(), nullable=False),
        sa.Column('title', sa.String(length=100), nullable=False),
        sa.Column('done', sa.Boolean(), nullable=False),
        sa.PrimaryKeyConstraint('id')
    )

def downgrade() -> None:
    op.drop_table('todos')
```

要点:
- `revision` = 本版本 id,`down_revision = None` 表示这是链条起点;下一个迁移文件的 down_revision 会指向它;
- `upgrade()` 和 `downgrade()` 互为逆操作:建表 ↔ 删表;
- **注意**:autogenerate 写的是"空 table 结构"——SERIAL 序列、default 这些在 PG 里是序列/默认值对象,Alembic 有自己的表达方式(见第 5 步的 add_column)。

执行迁移并验证:

```powershell
uv run alembic upgrade head
docker exec -i pg-school psql -U postgres -d todo -c "\d todos"
docker exec -i pg-school psql -U postgres -d todo -c "\dt"       # 多了 alembic_version 表!
docker exec -i pg-school psql -U postgres -d todo -c "SELECT * FROM alembic_version;"
```

`upgrade head` = 一路升到最新版本;`alembic_version` 表里那串 id 就是"当前在第几个版本"。

再验证服务能起来:uvicorn 启动 → lifespan 会自动补种那一条待办 → `curl http://127.0.0.1:8000/todos` 能查到。

## ➕ 第 5 步:加字段迁移 + 回滚(40 分钟)

给 Todo 加一个 `created_at`(创建时间),在 `models.py` 里:

```python
from datetime import datetime
from sqlalchemy import String, func

class Todo(Base):
    ...
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())
    # server_default=数据库侧默认:加列时库里已有的行会自动填 now()
    # 还记得吗?昨天说过 server_default "今天不用" —— 今天就是它的主场
```

为什么这里**必须** server_default?表里已有数据,`ALTER TABLE ADD COLUMN created_at NOT NULL` 时,**已有行这一列该填什么?** 没有默认值就直接报错。这是真实项目最常见的迁移翻车点。

生成第二个迁移:

```powershell
uv run alembic revision --autogenerate -m "add created_at"
```

打开新文件,对比第一个迁移文件,看它多了什么:

```python
def upgrade() -> None:
    op.add_column('todos', sa.Column('created_at', sa.DateTime(), server_default=sa.text('now()'), nullable=False))

def downgrade() -> None:
    op.drop_column('todos', 'created_at')
```

要点:① `down_revision` 现在指向第一个版本——**版本链**连起来了;② upgrade 加列,downgrade 删列,互为逆操作;③ `sa.text('now()')` 是"原生 SQL 片段",PG 的 now() 函数。

然后**跑一次完整的升级/回滚/再升级循环**,每步都验证:

```powershell
uv run alembic upgrade head                                    # 加列
docker exec -i pg-school psql -U postgres -d todo -c "\d todos"             # 看到 created_at
docker exec -i pg-school psql -U postgres -d todo -c "SELECT id, created_at FROM todos;"  # 老行已自动填时间

uv run alembic downgrade -1                                    # 回退一步:删列
docker exec -i pg-school psql -U postgres -d todo -c "\d todos"             # created_at 没了

uv run alembic upgrade head                                    # 再升回去
docker exec -i pg-school psql -U postgres -d todo -c "SELECT * FROM alembic_version;"   # 版本 id 变回第二个
```

再验证应用:API 启动正常、`uv run pytest` 9 个测试仍然全过(测试和真实库是同一个 todo 库;fixture 里的 create_all 只是保险——表已存在就跳过,不会动迁移建好的表。INSERT 不写 created_at,由 PG 的 server default 自动填——这也是 server_default 的好处之一)。

## 🎁 加餐:迁移文件里的 downgrade 为什么重要(5 分钟)

上线后发现新版本有 bug,要紧急回退:代码能 git revert,数据库结构靠 `alembic downgrade`——**upgrade 和 downgrade 必须成对写好**。autogenerate 自动生成逆操作,但像"删除一张表"这类操作,升级会丢数据,downgrade 也变不回来——所以生产上**有损迁移(drop table/column)要人工确认、备份先行**。今天你 drop 的 todos 只有练习数据;真实项目里这会是一份工单。
