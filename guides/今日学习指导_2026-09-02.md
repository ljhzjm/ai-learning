## 🎯 先懂 4 个概念(3 分钟)

| 概念 | 一句话解释 |
|---|---|
| **Depends 依赖注入** | 接口函数参数里写 `db = Depends(get_db)`,FastAPI 帮你**自动调用 get_db() 并传入结果**,接口代码不用自己 new 对象 |
| **异常处理** | 出错时主动 `raise`,FastAPI 统一返回干净 JSON;自定义异常 + `exception_handler` 全局兜底 |
| **中间件** | 每个请求**必经的关卡**,`@app.middleware("http")` 包住所有接口 —— 计时、打日志、加响应头都在这做 |
| **lifespan** | 应用**启动/关闭时只执行一次**的代码(预置数据、开连接、清理资源);它是旧写法 `@app.on_event` 的现代替代 |

四件套的共同思想:**把"准备东西、处理意外、横切逻辑"从接口函数里抽出去**,接口只写业务。

## ⚙️ 第 2 步:lifespan + 假数据库(25 分钟)

新建 `src\w1d5_fastapi_refactor\db.py` —— 用一个模块级变量当"内存数据库"(重启即清空,所以需要 lifespan 预置数据):

```python
# db.py —— 假数据库 + 自定义异常
class ItemNotFoundError(Exception):
    def __init__(self, item_id: int):
        self.item_id = item_id
        super().__init__(f"商品 {item_id} 不存在")

fake_db: dict[str, list[dict]] = {"items": []}
```

然后改 `main.py` 顶部:

```python
from contextlib import asynccontextmanager

from fastapi import FastAPI
from w1d5_fastapi_refactor.db import fake_db

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 启动时执行一次:预置数据
    fake_db["items"].extend([
        {"id": 1, "name": "键盘", "price": 299.5, "is_offer": False},
        {"id": 2, "name": "显示器", "price": 1299.0, "is_offer": True},
    ])
    print("[lifespan] 启动完成,预置 2 件商品")
    yield                       # ← 应用运行期间停在这里
    # 关闭时执行一次:清理
    print("[lifespan] 正在关闭,清理资源")

app = FastAPI(lifespan=lifespan)
```

> `yield` 之前 = 启动逻辑,`yield` 之后 = 关闭逻辑。保存后观察终端:uvicorn 自动重启会打印"启动完成",**Ctrl+C 退出**会打印"正在关闭"。以后数据库连接池、模型加载都放这里。

## 🔌 第 3 步:Depends 依赖注入,重构 3 个接口(30 分钟)

在 `main.py` 里写 3 个"依赖函数"(普通函数,接口里用 Depends 声明):

```python
from fastapi import Depends, Query
from w1d5_fastapi_refactor.config import settings

def get_settings():          # 依赖 1:配置
    return settings

def get_db():                # 依赖 2:假数据库
    return fake_db

def get_pagination(          # 依赖 3:分页参数(依赖里也能做校验!)
    skip: int = Query(0, ge=0),
    limit: int = Query(10, ge=1, le=100),
):
    return {"skip": skip, "limit": limit}
```

然后把昨天的接口逐个重构:

```python
# 接口 1:路径参数 + 注入配置
@app.get("/hello/{name}")
def hello(name: str, s = Depends(get_settings)):
    return {"message": f"Hello, {name}!", "from": s.app_name}

# 接口 2:查询参数 → 由 get_pagination 统一接管
@app.get("/items")
def list_items(p = Depends(get_pagination), db = Depends(get_db)):
    items = db["items"]
    return {"items": items[p["skip"] : p["skip"] + p["limit"]]}

# 接口 3:POST 现在真的写入"数据库"
@app.post("/items", status_code=201)
def create_item(item: Item, db = Depends(get_db)):
    new_id = max((i["id"] for i in db["items"]), default=0) + 1
    record = item.model_dump()      # Pydantic 模型 → dict
    record["id"] = new_id
    db["items"].append(record)
    return record
```

**验证**:重启后访问 `http://127.0.0.1:8000/items` —— 返回的不再是 range(100),而是 lifespan 预置的 2 件商品。POST 一件新商品再 GET,数据在(重启后消失,因为是内存库)。`limit=500` 会报 422 —— 依赖里的 `le=100` 在拦。

> 要点:**依赖函数可以有自己的参数**(get_pagination 的 skip/limit 来自查询参数),FastAPI 自动帮你层层解析。`item: Item` 请求体本质也是一种隐式依赖。

## 🚨 第 4 步:异常处理 —— 统一 404(25 分钟)

@app.get("/items/{item_id}")
def get_item(item_id: int, db = Depends(get_db)):
    for item in db["items"]:
        if item["id"] == item_id:
            return item
    raise ItemNotFoundError(item_id)   # 找不到 → 抛自定义异常

**② 注册全局异常处理器**(main.py 里,import `Request` 和 `JSONResponse`):

from fastapi import Request
from fastapi.responses import JSONResponse

@app.exception_handler(ItemNotFoundError)
async def item_not_found_handler(request: Request, exc: ItemNotFoundError):
    return JSONResponse(status_code=404, content={"error": "not_found", "message": str(exc)})

## ⏱️ 第 5 步:中间件 —— 每个请求都计时(20 分钟)

加在 `app = FastAPI(...)` 之后:

```python
import time

@app.middleware("http")
async def log_time(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)   # 放行给真正的接口
    elapsed = (time.perf_counter() - start) * 1000
    response.headers["X-Process-Time"] = f"{elapsed:.2f}ms"
    print(f"{request.method} {request.url.path} -> {response.status_code} ({elapsed:.2f}ms)")
    return response
```

**验证**:
1. 浏览器随便访问几个接口,看**终端**打出的访问日志
2. 看响应头有没有 `X-Process-Time` —— PowerShell 里用 `curl.exe -i http://127.0.0.1:8000/items`(注意是 `curl.exe`,`curl` 会被 PowerShell 劫持成别的命令)

> 洋葱模型:`call_next` **之前**的代码 = 请求进来时;`call_next` **之后** = 响应出去前(所以这里还能改响应)。这就是"横切逻辑"—— 不用在每个接口里重复写计时。

## 🎯 先懂 4 个概念(5 分钟)

| 概念 | 一句话解释 |
|---|---|
| **async/await** | 协程函数写 `async def`;`await` = "我在这等,但**让出执行权**,你先去干别的",回来再继续。全程**单线程** |
| **事件循环** | 单线程里的"调度员":哪个协程在等 IO 就挂起它、切去跑下一个。`asyncio.run(main())` 是启动入口 |
| **asyncio.gather** | 把一批协程**同时**交给事件循环,全部完成后一起拿结果 |
| **httpx.AsyncClient** | requests 的"异步版":`async with httpx.AsyncClient() as client` 复用连接池,请求写 `await client.get(url)` |

共同思想:**等网络/磁盘时 CPU 是闲的 —— 与其傻等,不如同时发 10 个请求**。注意:它**不是多线程**,CPU 计算该慢还是慢;它加速的是"大量 IO 等待"。

> 和昨天的联系:FastAPI 接口写 `def`/`async def`、lifespan 的 `@asynccontextmanager`,都跑在同一套东西上 —— uvicorn 内部就是一个 asyncio 事件循环。今天学的就是它的底层。

## ⏱️ 第 2 步:用 asyncio.sleep 理解"并发"(25 分钟)

新建 `src\w1d6_async_fetch\compare.py`(sleep 模拟"等待网络",不真联网):

```python
import asyncio, time

async def fetch(i: int):           # async def 声明协程
    await asyncio.sleep(1)         # 模拟:等网络 1 秒,await = 让出执行权
    return f"结果 {i}"

# 写法 A:串行 —— 一个一个等
async def serial():
    t0 = time.perf_counter()
    results = []
    for i in range(10):
        r = await fetch(i)         # 必须等完 1 秒才轮到下一个
        results.append(r)
    return results, time.perf_counter() - t0

# 写法 B:并发 —— 一起等
async def parallel():
    t0 = time.perf_counter()
    results = await asyncio.gather(*[fetch(i) for i in range(10)])
    return results, time.perf_counter() - t0

async def main():
    r1, t1 = await serial()
    r2, t2 = await parallel()
    print(f"串行 10 个:{t1:.2f}s  并发 10 个:{t2:.2f}s  提速 {t1/t2:.0f} 倍")

asyncio.run(main())   # ← 事件循环的启动入口,永远在脚本最底部
```

**验证**:`uv run python src/w1d6_async_fetch/compare.py` → 串行约 10s、并发约 1s。如果两行都是 10s,检查是不是忘了 `gather`。

> 要点:**只有 `await` 点才是"让出"点**。串行写法每次 await 都傻等;gather 把 10 个协程一次全交出去,事件循环在它们之间来回切。

## 🚀 第 4 步:gather 并发抓 10 个 URL + 计时对比(40 分钟)

新建 `src\w1d6_async_fetch\fetch_many.py`:

```python
import asyncio, time, httpx

URLS = [
    "https://api.github.com/repos/fastapi/fastapi",
    "https://api.github.com/repos/encode/httpx",
    "https://api.github.com/repos/psf/requests",
    "https://api.github.com/repos/astral-sh/uv",
    "https://api.github.com/repos/pydantic/pydantic",
    "https://api.github.com/repos/python/cpython",
    "https://api.github.com/repos/microsoft/vscode",
    "https://api.github.com/repos/nodejs/node",
    "https://api.github.com/repos/docker/compose",
    "https://api.github.com/repos/redis/redis",
]

async def fetch(client: httpx.AsyncClient, url: str):
    t0 = time.perf_counter()
    r = await client.get(url)
    dt = (time.perf_counter() - t0) * 1000
    return f"{r.status_code}  {dt:6.0f}ms  {url}"

async def serial(client):
    t0 = time.perf_counter()
    for url in URLS:
        print(await fetch(client, url))
    return time.perf_counter() - t0

async def parallel(client):
    t0 = time.perf_counter()
    lines = await asyncio.gather(*[fetch(client, u) for u in URLS])
    for line in lines:
        print(line)
    return time.perf_counter() - t0

async def main():
    async with httpx.AsyncClient(timeout=10) as client:
        t_s = await serial(client)
        print(f"\n串行总耗时:{t_s:.2f}s\n" + "=" * 50)
        t_p = await parallel(client)
        print(f"\n并发总耗时:{t_p:.2f}s  提速 {t_s/t_p:.1f} 倍")

asyncio.run(main())
```

**验证**:并发总耗时接近"最慢的那一个请求",而不是 10 个之和 —— 这是今天最重要的观察。

> 要点:`gather` 等的是"最慢的一个",不是"所有加起来";瓶颈从「10 个串行」变成「1 个慢请求」。返回顺序 = 传入顺序,和谁先完成无关。

## ⏰ 第 5 步:超时 —— 两层保险(30 分钟)

**① 单请求超时**:建 client 时 `timeout=10`(第 3 步已写)—— 每个请求最多 10 秒。
**② 整体超时**:整个任务最多 N 秒,到点放弃剩余:

```python
try:
    lines = await asyncio.wait_for(
        asyncio.gather(*[fetch(client, u) for u in URLS]),
        timeout=8.0,               # 整个 gather 只给 8 秒
    )
except asyncio.TimeoutError:
    print("8 秒没跑完,整体放弃!")
```

**③ 必做的实验**:在 URLS **末尾混一个黑洞地址**(不可路由,永远不响应),跑一遍观察:

```python
URLS += ["http://10.255.255.1/"]
```

- 只开 `timeout=10`:那个请求 10 秒后报错,其余 9 个正常 —— 但**注意:一个协程抛异常,整个 gather 都会被炸掉**,这正是下一步要解决的问题
- 再加 `wait_for` 整体超时:到点立刻收工
